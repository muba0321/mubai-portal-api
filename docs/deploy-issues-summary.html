二、部署过程中的问题与解决

问题 1 旧容器残留冲突

服务器上存在旧的 sre-portal-nginx 容器（未启动）和 mysql8 容器（端口 13306，重复部署），占用容器名称和端口资源。

解决方案

# 删除未使用的 nginx 容器
docker stop sre-portal-nginx && docker rm sre-portal-nginx

# 删除重复的 mysql 容器
docker stop mysql8 && docker rm mysql8

# 清理悬空镜像
docker image prune -f

最终只保留：sre-portal-backend、sre-portal-frontend、sre-portal-mysql 三个核心容器。

问题 2 旧后端容器名称冲突

执行 docker compose up -d 时报错： Conflict. The container name "/sre-portal-backend" is already in use。 docker compose down 无法清理旧容器，导致新构建的镜像无法启动。

解决方案

# 强制删除旧容器后再启动
docker rm -f sre-portal-backend 2>/dev/null
docker compose up -d

优化：在部署脚本中，docker compose down 之前先执行 docker rm -f 强制清理，确保名称可用。

问题 3 前端 Dockerfile pnpm 版本不兼容

前端 Dockerfile 中使用 corepack prepare pnpm@latest 安装 pnpm， 但 pnpm@11+ 与 node:20-alpine（Node 20.20.2）不兼容，构建时报 ERR_UNKNOWN_BUILTIN_MODULE 错误。

解决方案

# 修改 Dockerfile
RUN npm install -g pnpm@9  # 降级到 pnpm@9，兼容 Node 20 Alpine

同时将 pnpm build 改为 npx vite build，跳过 TypeScript 类型检查（项目本身有 TS 类型问题）。

问题 4 Docker 镜像构建缓存导致 .env.production 不生效

构建时 .dockerignore 文件排除了 .env.production， 虽然之后从 .dockerignore 中移除了，但 Docker 层缓存导致 RUN npx vite build 步骤仍然使用旧缓存，构建产物中 VITE_APP_BASE_API 未被注入。

解决方案（两步）

# 第一步：从 .dockerignore 中移除 .env.production
# 让 Docker COPY . . 时包含 .env.production

# 第二步：使用 --no-cache 强制重建
cd /opt/sre-portal/frontend && docker build --no-cache -t sre-portal-frontend .

# 清理构建缓存确保干净
docker builder prune -af

经验教训：修改 .dockerignore 后，后续构建必须使用 --no-cache， 否则 COPY 层缓存仍然不包含被忽略的文件。这是 Docker BuildKit 的已知行为。

问题 5 前端 API 请求路径与 nginx 代理不匹配

前端浏览器实际请求的是 /api/v1/auth/login（405 错误）， 而 nginx 只配置了 /prod-api/ 的代理规则。 原因：前端构建时 VITE_APP_BASE_API=/prod-api 没有被 vite 正确注入， baseURL 变成了空字符串，导致请求直接发到 /api/ 而非 /prod-api/api/。

解决方案：nginx 同时代理两条路径

# 同时支持 /prod-api/ 和 /api/ 两个前缀
location /prod-api/ {
    proxy_pass http://sre-portal-backend:5000/;
    ...
}

location /api/ {
    proxy_pass http://sre-portal-backend:5000;
    ...
}

这样无论前端 baseURL 是空、/api 还是 /prod-api， nginx 都能正确代理到后端，彻底消除前端构建时环境变量注入的不确定性。

问题 6 前端端口映射从 80 改为 3000

初始配置前端容器映射为 3000:80（容器内 nginx 监听 80）， 用户要求容器内外端口一致，都使用 3000。

解决方案：三处同步修改

文件修改内容
nginx.conflisten 80 → listen 3000
DockerfileEXPOSE 80 → EXPOSE 3000
docker-compose.yml3000:80 → 3000:3000

问题 7 Docker Compose 前端 build context 路径解析错误

在服务器的 /opt/sre-portal/backend/docker-compose.yml 中配置 context: ../../01-frontend/sre-portal-frontend， Docker 解析为 /opt/01-frontend/...（少了 sre-portal 一级目录）， 导致构建时找不到前端源码。

解决方案

放弃从 docker-compose 中 build 前端，改为：

# 在前端源码目录单独构建
cd /opt/sre-portal/frontend && docker build -t sre-portal-frontend .

# 打标签让 docker-compose 能找到
docker tag sre-portal-frontend backend-sre-portal-frontend

# docker-compose 中改用 image 而非 build
# services.sre-portal-frontend.image: sre-portal-frontend

五、经验总结与最佳实践

Docker 构建必须考虑缓存

修改 .dockerignore 后，后续 docker build 需要使用 --no-cache 强制重建。 COPY 层的缓存是独立的，不会自动感知 .dockerignore 的变化。 更安全的做法：将 package.json 和 .env.* 分层 COPY，确保环境配置文件不被忽略。

容器名称冲突需强制清理

docker compose down 在某些情况下不会删除容器， 建议在部署脚本开头统一执行 docker rm -f 容器名 2>/dev/null 强制清理。

代理配置要兼容多种前缀

当不确定前端 baseURL 是否准确注入时，nginx 同时代理 /api/ 和 /prod-api/ 是更保险的做法， 避免前端构建问题导致线上不可用。

alpine 镜像的兼容性注意

Node.js Alpine 镜像中安装 pnpm 时，corepack 安装的最新版 pnpm 可能与 Alpine 的 musl libc 不兼容，建议固定版本 npm install -g pnpm@9。

前后端分离部署的端口统一

容器内外端口保持一致（如都用 3000），便于记忆和排查问题。 如果 nginx 默认 80 端口，在 docker-compose 中映射为 3000:80 会导致容器内实际监听端口与外部不一致，增加排障难度。
